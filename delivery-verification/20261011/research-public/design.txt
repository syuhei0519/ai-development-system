3. API・Account関連の確定提案 [E-API]
比較軸: 最小scope、既存Account非変更、独立起動/障害、削除時整合性、テスト容易性。
採用: immutable Order。id=正のint64（DB identity）、account_id=必須正のint64の履歴参照、item_code=ASCII [A-Za-z0-9][A-Za-z0-9._-]{0,63}、quantity=整数1〜999、created_at=DB TIMESTAMPTZ/UTC RFC3339。価格、状態遷移、明細配列、Payment、Notification、一覧/更新/削除APIは今回追加しない。
POST /api/orders: Content-Type application/json（charset=utf-8許容）、body {"account_id":1,"item_code":"SKU-001","quantity":2}。201とLocation: /api/orders/<id>、body {"id":1,"account_id":1,"item_code":"SKU-001","quantity":2,"created_at":"2026-10-10T00:00:00Z"}。id/timeは入力不可。DB commit後のみ201。idempotencyは今回なし、POST自動再試行なし（通信断時重複作成可能をAPI文書へ明記）。
GET /api/orders/{id}: 200同表現、未存在404。path IDは[1-9][0-9]*かつint64上限以内。POST/GET以外のmethodは405/Allow、未知path404。
入力境界: 未知/重複key、欠落/null、空body、非object、型違い、少数/指数表記の整数入力、末尾JSON、壊れたJSON、範囲外は400 validation_error。item_codeはtrimせず空白を拒否。本文16KiB超413 payload_too_large、非JSON media type415 unsupported_media_type。検証失敗ではStore呼出し/DB書込み0。error bodyは {"error":{"code":"...","message":"..."}}。not_found404、DB利用不能503 unavailable、その他500 internal_error。SQL/DSN/本文/Secretを応答・ログへ出さない。GET /livez=プロセス200、GET /readyz=Order DB接続とOrder履歴version1を1秒で検証し200/503、shutdown時503。
Account整合性: account_idは所有権/認証/現存保証ではない履歴上の外部参照。Account API照会や跨DB FKを行わず、Account削除後もOrderを保持して同一account_idを返す。存在しない正のaccount_idも受け付ける。この仕様をOpenAPI/README/試験で明記する。新規Account作成や既存行の更新/削除はOrderコードから行わない。Account削除時のcascade/restrictも追加しない。
不採用: 同期Account存在照会は障害依存と削除との競合を生み、永続FK保証にはならない。共有DB FK+削除制限/cascadeはAccount DELETE契約/データ非変更を侵す。分散transaction/tombstone/event連携はscopeを超える。Account関連なし案は最小だが将来参照を表現できないため、保証範囲を明示した履歴参照を選ぶ。認証/利用者別認可は既存同様未提供、ClusterIP限定の隔離lab用途。外部公開は別設計/許可を要する。

4. DB・migrationの確定提案 [E-DB]
候補A=専用PostgreSQL/DB/role/PVC。利点はAccountにDDL/管理接続不要、障害/削除/履歴の分離。欠点は追加Pod、2Gi PVC、backup/patch/Secret運用。候補B=同instance別DB/role。資源を節約しengine運用を再利用できるがCPU/接続/障害を共有し、既存PVCへ管理者DDLが必要。初期化scriptの追記では既存DBに適用されず、別の承認済み運用手順が要る。候補C=同DB別schemaは権限/search_path誤りの波及が大きく、共有schema/historyはAccount Readyを破壊する。
採用A。安全性とAccount非変更を運用コストより優先する。コードはDSN境界により将来Bへ移せるが、今回B用の管理DDLや接続は実行しない。既存chartの抽象化でAccount資源を再命名する案も不採用。新charts/order-postgresqlに既存安全設定を明示的に再利用し、差分をレビューする。
Order DB=orders、role=order_app（LOGIN/NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOINHERIT、orders所有者）、別Secret order-db。admin-password/app-username/app-passwordの既存キー契約を再利用。runtimeとmigrationはappキーのみ、adminはDB初期化のみ。runtimeにDDL可能なDB ownerを使う既存lab方式は残余リスクとして記録し、Account/他DBへの権限を与えない。将来runtime専用DML roleへ分離可能だが今回新認証基盤は要求しない。
SQL: orders(id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, account_id BIGINT NOT NULL CHECK(account_id>0), item_code VARCHAR(64) NOT NULL CHECK(item_code ~ '^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$'), quantity INTEGER NOT NULL CHECK(quantity BETWEEN 1 AND 999), created_at TIMESTAMPTZ NOT NULL DEFAULT now())。account_idにFKなし。SQLはparameterized INSERT RETURNING/SELECT、各操作3秒、pool最大5、connect3秒。履歴order_schema_migrations(version INTEGER PRIMARY KEY, applied_at TIMESTAMPTZ NOT NULL DEFAULT now())、初版1、独立embed directory、独立advisory lock=7742340082。AccountのSQL/embed/history/lockを変更しない。Order接続はcurrent_database()='orders'かつcurrent_user='order_app'を起動/migration前に確認し、誤接続は書込み前に拒否。これは認証/権限設定の代用品ではない。
Order migrationは既存有限待機/170秒/SQL単位transaction/履歴同時commit/lock取消時connection破棄/5秒cleanup方式を再利用。既存packageの破壊的共通化はしない。新SQLはforward-only、既存SQL編集・down migration・Accountデータ修復は禁止。再適用はno-op。失敗はJob非0でDeploymentを止め、履歴を手で成功化しない。

5. image・CI・Trusted Manifest [E-RELEASE]
B:.github/workflows/ci.yml、ci/github/oci.sh、release.pyは1image/1artifact/1release契約。publishはprotected main push+ENABLE_GHCR_PUBLISH+ghcr-publish承認、proposeはENABLE_MANIFEST_PR+manifest-update承認。ci-resultはpublish/proposeを集約しない。M:ci/github/release.pyはbackend/frontendだけを認め、source main一致、latest run/attempt、匿名GHCR、record/SBOM/checksumを検証。trusted-render.py/validate.shは3chart固定。このままOrderを足すと検証漏れ/誤同定となる。
比較: 単一imageの起動arg切替は独立image要件/責任を曖昧にするため不採用。別repo新設は指定scope外。同repoの専用Dockerfile.orderとcmd/order-serverを採用。Go依存/固定base/nonroot/read-only/drop capabilities/scanを再利用。実行path=/order-server、migrate subcommand、port8080。既存Account imageは変更しない。amd64単一platformを維持し、index digestとplatform digestの取り違えを回避する。
B2 CI: image jobをbackend/order matrix（fail-fast=false）へ拡張し、全件成功をci-resultが必要とする。各imageを1回buildしたOCI tarからreader/runtime/scan/SBOMを検証し、その同一tarをpublish。共有source scanは同SHA/checksumで結合し、作業dir/出力/成果物をservice別に分離。Account artifact名checked-image-<attempt>、release tag gha-<sha>-<run>-<attempt>、v1 record、image ghcr.io/syuhei0519/backend-appを維持。Orderはchecked-image-order-<attempt>、published-evidence-order-<attempt>、tag gha-order-<sha>-<run>-<attempt>、image ghcr.io/syuhei0519/backend-app-order。asset名release-record.json/sbom.cdx.json/image-scan.jsonは別release内で再利用。並列release作成の同名上書きを禁止し、失敗時は未公開側を成功扱いしない。publish/proposeは別jobでも既存Environmentと最小token権限を維持。
Order recordは新schema core-platform/github-release/v2、v1の全必須bindingにservice='order'を追加。repositoryはsource repo backend-appのまま、imageRepositoryは固定対応表で分離。manifest release.schemaVersion='github-v2'、service='order'を追加。他fieldsはsourceRepository/sourceCommit/runId/runAttempt/recordUrl/recordSha256/sbomUrl/sbomSha256。Orderにも既存account.lab/* annotation prefixを互換目的で使用しservice annotationを追加。prefix名称はAccount DBアクセスを意味しない。
M0 verifierはv1 backend/frontendをそのまま受理、新v2はorder→backend-app→backend-app-orderの完全一致だけ許可。image名からsource repoを推測しない。record schema/サービス/registry/source/ref/run/attempt/digest/config/archive/SBOM/checksum/expiry/最新mainとworkflowを照合。canonical artifact ZIP単一record規則をservice別artifactへ適用。Orderをbackend recordで偽装、別run混入、欠落matrix、期限切れ、tag移動、再build、未知service/pathは拒否。propose先はenvironments/local/order.yaml固定、service別branch、PRのみ。producerとconsumerで同じfixtureを使う。
Trusted renderのinventoryはfrontend/backend/postgresqlにOrder/order-postgresqlを追加。baselineに新chartがないときだけ不在を許し、chartとvalues片方欠落・未知chart・未走査PodSpecは拒否。active/inactiveの固定inventoryをtrusted main側で管理し、PRの任意リストで検査対象を減らせない。新DB imageはGHCR app証跡として扱わず、既存postgres chartと同じ固定repository/tag/digestとsecurity基準を明示allowlist化。新DB workloadの差分もinventory/scan/PVCポリシー対象にする。
M0はlive既存render不変で先行main化可能。M1の新chartはenable=falseを既定にし、CI専用fixtureでenable=trueをlint/render/検査する。実digest未取得のplaceholderをlive enabled manifestに入れない。M2で公開済みOrder digestを選択し同SHAのtrusted mainで認証付き検証する。鮮度は現行15分上限とrelease期限の短い方、変更時再検証。期限切れ証跡を延長・転用しない。

6. Helm・Argo・配備境界 [E-DEPLOY]
新Service/Deployment/SA/ConfigMap/Job名はorder/order-config/order-migration、DB資源はorder-postgresql/order-postgresql-init/order-postgresql-data。namespaceは既存accountを採用し、新namespace/AppProject権限拡張を避ける。独立namespaceは将来強い境界になるが今回独立Service要件には不要。同namespaceはセキュリティ分離保証ではない。
Order=ClusterIP8080、replicas1、startup/liveness=/livez、readiness=/readyz、SA automount=false、UID10001、read-only root、/tmp emptyDir。DBホストorder-postgresql、DB orders、app Secret order-db。Order JobはDeploymentと厳密に同じtag@digest、Sync wave -10、ConfigMap/SA -20、Deployment0、deadline180/backoff1/Never、BeforeHookCreation/HookSucceeded。Secret/NamespaceはMで生成しない。DBには既存固定postgres17.10 digest/security/resources（requests100m/256Mi、limits500m/512Mi、PVC2Gi）を再利用。PVC Prune=false,Delete=false、StatefulSet Prune=confirm,Delete=confirm。

P rootがmain自動同期するのでP1 mergeはautomatic配備影響。M既存chart変更もmain追跡によるautomatic、変更範囲を証明できなければunknown。M0/M1/P0はrender不変/未登録/disabledをテストで証明できた範囲のみnone提案。noneはコード名称だけから決めない。Bはimage公開/manifest PRを作るがclusterを直接変えず、digest固定既存配備は自動更新されない（none提案、ManagerがPR差分再確認）。
有効化前に運用者が新PVC容量、order-db metadata、固定image匿名pull、対象context、backup/復旧、承認を確認する。失敗時は後続enable/選択更新を停止し、Accountは維持、Orderの失敗Jobと非秘密statusを保存。初回は既知良好Order revisionがないので架空のrollback先を指定しない。許可済み手順でOrder appのみ同期停止/無効化しPVC保持、修正forward migrationを再検証してApplication全体sync。既知良好版ができた後もschema互換と証跡鮮度確認なしに古いdigestへ戻さない。

7. AC原文・最早検証段階とTest境界 [E-TEST]
全件出典: https://github.com/syuhei0519/backend-app/issues/2。
AC-1: 作成したOrderが再起動後も取得できる
最早premerge。DB永続volumeを残しHTTPプロセスを停止→新プロセスを同DBへ起動→GET一致で達成を検証できる。kind未準備を延期理由にしない。隔離DBでcreate後id/account/item/quantity/created_atを保存、PID変化を確認、メモリStore再利用なしでGET一致。DBコンテナ再起動+同volumeで同じ検査も行い、PVC破棄/cluster再作成耐性とは区別する。kind rollout後同試験は追加の配備回帰。
AC-2: 不正入力は4xxとなりAccount CRUDが維持される
最早premerge。Unitでは入力境界とerror mapping、Store未呼出し、HTTP routes/headersを実測。Integrationでは実HTTP+実Postgresで正常/全不正入力と書込み0、Account create/list/get/update/delete、重複email409/未存在404、Account Readyを確認。CRUD用に新規作成する行と保全用sentinel行を分離し、Order migration/再起動の前後で既存Account sentinel fixtureの全列とschema_migrations(version/applied_at)を比較し不変。Account削除後のOrder GET保持、未存在account_id受理も確定仕様として検査。DB障害503は4xx入力試験とは別。Unitや通常go testのDB SkipをIntegration合格にしない。
AC-3: 独立ServiceがSyncedかつHealthyになり対応image digestが確認できる
最早premerge。独立ServiceとArgoのSynced/Healthy・digest一致は隔離kindに候補M/P revisionを登録して確認できる。Issue原文はmain反映後だけの観測を要求していない。Bのmain限定公開をPのマージ後条件へ誤転用しない。B1/B2 PRはAC-1/2を主対象としAC-3未検証を保持、B2マージと承認付きGHCR公開後、M2/P1のマージ前に正規公開imageと候補M/Pの固定40桁revisionでT6を行う。M/P候補は既存認可済みfeature refから読ませ、protected-mainによるimage証跡検証は維持する。候補Git参照が取得できない場合はpremerge blockedでありpostdeployへ再分類しない。
AC-3試験のowner=独立Test Agent、配備操作=承認済み運用者。environment=専用kind-core-platform-order-acceptance、専用kubeconfig、account namespace、Argo、Accountは新規fixture。method=採用B/M/P SHA・GHCR record/run/digestを固定しApplication.spec.source.targetRevision/status.sync.revision一致、Synced/Healthy、operation終端Succeeded、order-migrationの同revision成功、Service endpoint、Pod ready、container imageIDとrecord/manifest digest一致を確認。成功hookの削除前証跡またはArgo operation syncResultを保存。failure_action=該当M/P PRマージ停止、Issue未完了、6節復旧、修正後Test/Review再実行。分類根拠=P ApplicationのGit revision指定とArgo観測、B/Mの正規公開/検証はPマージ前に順序上成立可能。
必須AC3件に真のpostmerge/deploy限定項目はない。全verification_phase=premerge、deferred=nullを提案する。正規main統合後のArgo revision、imageID、Account/Order回帰はpostdeployの統合確認として別途必須。これは候補合格の転用ではなく、実際に統合/配備されたidentity確認であり、Issue Completionの集約証跡に含める。そこで失敗すればIssue未完了・復旧/再検証。全製品ACは本Researchではunverifiedである。
Test計画: T1 Unit（DB/cluster不要、go test ./internal/order/... ./internal/orderhttp/...等と全既存go test、race/vet）。T2 Integration（新専用harness、HTTP+実DB、AC-1/2）。T3 migration（fresh/no-op履歴不変/競合timeout/cancel/途中DDL rollback/retry/誤DB拒否）。T4 OCI（両imageの正確なtar、networkなしruntime、scan/SBOM、service混同拒否）。T5 Helm/GitOps（全enabled/disabled、lint --strict/template/schema/Kubeconform/security/全PodSpec inventory/既存Account render不変/Secret未生成/PVC保持）。T6 premerge隔離kind+Argoリハーサル（候補固定版、migration失敗時停止/復旧、Account/Order CRUD、restart）。T7 postdeploy正規統合版のAC-3再確認とAC-1/2配備回帰。T1〜T7は今回未実行、提案である。
T2/T3はkind不要の専用DBコンテナでもよいが運用者許可が必要。既存TestMigrationDisposableDatabaseのcontext/loopback guardを削除しない。新harnessは新しく作成したdisposable DBのみ、固定DB名/role/専用port、既存volume reuse拒否、明示opt-in、限定cleanup、ログからDSN除外、未指定はskipを結果に明記。T6は専用contextとkubeconfig、既存clusterへ接続しない。premerge試験が未実行なら該当PR mergeはblockedのまま。

8. 変更単位、担当、受入、順序 [E-PLAN]
以下はManagerが独立タスクへ割り当てる単位。担当Implementationと独立Test/Reviewを分離する。全PR共通premerge条件=固定head/base/config、通常CI、独立Test、AI Review、GitHub必須checks/reviews/ruleset/queue、明示merge許可、依存/鮮度。PR未作成なので番号/headを捏造しない。全PRはIssue通常リンクのみ、自動close禁止。
B1 backend API/永続化: Implementation Backend Agent。対象は3節/4節、cmd/order-server、独立設定/health/shutdown、新API文書とT1/T2/T3 harness。Account公開image/CIは維持。受入はAPI契約全件、独立migration、Accountデータ/履歴不変、AC-1/2実DB合格。premerge=T1/T2/T3+既存Account回帰、SQL/DB boundaryレビュー。postdeploy=T7でAPIと永続化再確認。必要承認=Manager実装/merge、DB試験の使い捨て環境許可。前依存=本設計採用とupstream配送ゲート。最初の安全スライスはこのPR内部のdomain/HTTP/SQL定義/Unit。DB試験未許可でもコード作業可、未試験のPR merge不可。
